# VaultSync

macOS 原生 Obsidian 文库同步应用。支持多个 Vault、多台 Mac、Tailscale 网络、离线版本保留，以及联网后的差异比较和确认合并。

## 运行

按下方步骤构建后，可在 `dist/` 找到 `VaultSync.app` 和 `VaultSync-0.2.6.zip`。把应用放入“应用程序”（也可使用 `~/Applications`）再打开。安装包同时包含 Apple Silicon 和 Intel 可执行代码，最低 macOS 13。

这是本地构建的 0.2.6 版本，采用 ad-hoc 签名，尚未经过 Apple Developer ID 签名和公证。拷贝到其他 Mac 后，macOS 可能要求在“系统设置 → 隐私与安全性”中由你确认打开。首次使用先添加一个测试文库副本，验证你的实际设备环境。

### 从旧版升级

从 0.2.5 升级时，退出 VaultSync，再用新版替换原位置的 `VaultSync.app` 并打开。应用继续使用原有文库映射、版本历史和配对。

0.2.5 完成内部命名统一，默认数据目录为 `~/Library/Application Support/VaultSync/`，应用标识为 `app.vaultsync.mac`。升级已有安装前，先退出所有设备上的旧版，将旧数据目录完整迁移至新目录，保留设备证书、settings.json、Objects 和 LocalState；迁移同步引擎配置中的目录路径与传输目录 ID。所有配对设备必须一并升级后才能继续互相同步。不要直接启动新版创建空配置，也不要改写已有不可变版本对象。应用标识更换后，macOS 会重新请求文稿目录访问权限；请在每台 Mac 上允许访问已有文库，并检查需要的登录启动设置。

**0.2.2 修复会产生错误删除的扫描缺陷，所有设备均应升级。** 旧版在忽略 `.DS_Store` / `.tmp` 等普通文件时错误调用了“跳过子目录”，使仍存在的其他文件未被扫描。不要再次使用 0.2.1 或更早版本扫描真实文库。已受影响的数据需要从保留的版本内容恢复；单纯升级不会自动撤销已产生的错误删除。

0.2.2 同时加入接收百分比、剩余数据与“校验 / 写入本机文库”的阶段提示，避免把“设备已连接”理解为文件已经写回。移除或重加映射会取消旧扫描的后续工作，并按完整映射重建缓存。取消会在当前文件读取结束后生效；系统文件服务长时间阻塞时仍可能需要退出并重新打开应用。

0.2.1 修复主程序异常退出后残留同步引擎的问题。Air 曾因两个旧引擎占用 AppTranslocation 临时目录而无法打开（-47）；正常关闭残留引擎后已恢复打开。新增的独立生命周期组件会在主程序退出或崩溃后关闭引擎，包括主程序被强制结束的情况。无需清空文库或重新配对。

0.1.1 修复了官网版 Tailscale 在 Finder 启动环境下可能进入 GUI 模式、返回非 JSON 文本，导致“数据格式不正确”的问题。应用会显式设置 `TAILSCALE_BE_CLI=1`，并在某个 CLI 入口不可用时尝试其他已安装入口。解析失败会显示具体的 Tailscale 状态提示。实现依据：[Tailscale 官方 CLI 文档](https://tailscale.com/docs/reference/tailscale-cli?tab=macos)。

## 连接两台或更多 Mac

1. 两台都使用 0.2.5 或更新版本，并加入同一个 Tailscale 网络。访问策略需允许设备之间 TCP **22080**（同步）与 **22081**（设备发现 / 配对）。
2. 两边在“设备”页启动同步。在其中一台点击“查找设备”，从列表中选择另一台并点击“请求配对”。
3. 另一台会显示请求和六位数字。核对两边数字相同后，在接收方点击“确认配对”，自动完成双向配置。可以先后操作，请求保留约 10 分钟，无需同时点击。
4. 页面会显示“等待确认”“双向配对完成”及引擎的“已连接”状态；失败会直接说明原因。旧版本曾手动添加但没连通的设备，可以点击“重新请求配对”。
5. 第一台添加文库，新同步关系的 ID 留空。其他设备添加对应文件夹并使用相同文库 ID；请求确认后，也可从“配对设备的文库”列表选择。
6. 对其他 Mac 和文库重复上述操作。文库数量和设备数量没有写死配额，实际受本机资源影响。

发现仅探测 Tailscale 已知的在线设备，不扫描公共地址或整个局域网；发现阶段不发送文库名称或内容。对端确认后才交换文库目录，再由已有 Syncthing 设备证书验证真实身份并同步。对端应用、Tailscale、macOS 防火墙或端口策略影响连接时，会显示错误或等待状态。

仍保留“手动粘贴配对信息”以兼容旧版；输入错误直接显示在窗口内，取消不会再冒出被遮挡的旧错误。自动请求确认需要两边都运行 0.2.0 或更新版本。

每台设备的本地文件夹路径可以不同。配对信息只在复制时生成；后来增加文库，可以直接复制该文库 ID，不需要重新配对设备。

### 可选的 Base

在常在线的 Mac 上打开“设备”，启用“将此 Mac 设为 Base”。新 Mac 使用 0.2.6 或更新版本查找设备时，列表会优先显示在线的 Base。选择 Base 并完成双向配对即可。需要额外直连时，可展开“其他设备（可选直连）”。Base 开关只影响设备发现，已有配对照常同步。

Base 收到版本后，可以在其他设备稍后上线时把版本同步给它们。只配对了 Base 的设备可在 Base 离线期间继续编辑，版本会在连接恢复后交换。

**同步范围：所有配对设备会收到本机版本传输目录内的全部文库历史。** 本地添加哪些文库映射决定哪些文库会写回本机文件夹；此版本没有按设备隔离历史内容。设备移除会停止后续传输，但无法撤回对端已经收到的副本。

0.2.0 还修复了自动启动同步时从后台线程更新界面导致的闪退。界面状态现在统一由 MainActor 更新。

## 离线与冲突

- 应用运行时收集已落盘的文件状态；离线时也会生成本地版本。
- 同一文件有独立修改时，各分支进入“待合并”。分叉期间，本机当前内容保持可编辑，其他文件继续同步。
- “显示 diff”比较任意两个文本分支；“生成三方合并预览”使用共同祖先计算草稿。
- 存在重叠时，需要手动编辑并移除冲突标记。没有唯一共同祖先、删除与修改冲突、多分支复杂冲突，均可手动比较并填写结果。
- 每次确认都会生成具有全部当前分支为父版本的新版本；原始分支保留。晚到设备的旧分支仍可再次参与合并。
- 如果确认前本机或远端分支发生变化，会拒绝旧合并结果，并保留草稿供重新核对。
- 图片、PDF 等二进制附件可以导出和选择保留某个版本；其他版本仍在历史中。
- “版本历史”支持已删除文件，恢复会产生新版本。存在未解决分支时需先合并。

关闭主窗口后继续在菜单栏运行。退出应用或机器睡眠时不会收集编辑的中间状态；重新启动或唤醒后扫描当前文件并继续交换。它是文件版本同步工具，不提供逐键实时协同编辑。

## 文库设置

默认同步普通文件和附件。添加文库时可选同步 `.obsidian` 设置、主题与插件。布局文件 `workspace.json`、`workspace-mobile.json`、`workspaces.json` 保留在各设备本机；`.git`、`.trash`、系统临时文件不参与同步。插件配置可能含本机路径或凭据，启用前按需要选择。

同步的设置和插件变更可能需要重启 Obsidian 才能生效。

软链接不跟随。远端路径会校验，文件大小写或文件/文件夹名称冲突会暂停相关路径并显示提示；请在原设备统一名称后处理。

当前按文件版本同步，空文件夹不单独传输，重命名表现为旧路径删除与新路径新增。文件落盘与编辑器写入采用内容复核与原子替换；请先在副本文库验证你的编辑器和其他文件工具的写入方式。

## 数据位置

默认：`~/Library/Application Support/VaultSync/`。

| 路径 | 用途 | 参与传输 |
|---|---|---|
| `Objects/<vault-id>/blobs` | 按 SHA-256 寻址的文件内容 | 是 |
| `Objects/<vault-id>/revisions` | 不可变版本及父版本关系 | 是 |
| `LocalState` | 本机已应用版本与路径映射 | 否 |
| `Drafts` | 未完成的合并草稿 | 否 |
| `settings.json` | 本机设备、文库与偏好 | 否 |
| `Syncthing` | 设备私钥、API key、传输数据库与日志 | 否 |
| `Recovery` | 故障恢复时隔离的版本、状态快照和旧应用备份 | 否 |

此版本持续保留历史，未启用自动清理。版本目录包含笔记明文内容；网络传输经过 Syncthing 身份验证与 Tailscale 加密。请将应用数据目录与文库一起纳入 Time Machine 等独立备份。不要通过另一个同步工具同时修改同一份正在使用的 Vault。

应用监听文库和版本对象目录，按变更增量检查，空闲时不循环扫描。启动时检查程序关闭期间的变更；选择「立即扫描」或系统报告监听事件丢失时会重新核对相关目录。新到的内容对象仍校验 SHA-256，确认合并前仍核对本地编辑和最新版本。

## 源码构建与验证

需要 Swift 命令行工具（当前在 Swift 6.3 / macOS 26.3.1 上验证），无需完整 Xcode 或第三方 Swift 包。

```sh
swift run --scratch-path .build/work/build VaultSyncChecks
zsh scripts/build-app.sh
zsh scripts/package-release.sh
```

构建脚本分别编译两个 CPU 架构，合并为 universal app，并进行本地签名校验。引擎缺失时会调用 `scripts/fetch-syncthing.py` 从官方 GitHub 发布下载固定版本并校验 SHA-256；这是传输完整性校验，脚本没有执行 PGP 签名验证。

真实引擎集成验证需要本机 Tailscale 已连接：

```sh
python3 scripts/integration-check.py
python3 scripts/lifecycle-check.py
python3 scripts/startup-check.py
```

请先构建应用以下载验证所需的引擎。集成脚本会在工作目录中创建隔离文库，运行四个真实 Syncthing 进程，验证三台互连时第四台只连 Base 的双向同步，以及附件、多 Vault、离线分叉、显式合并和晚到设备收敛。端口使用 `28500–28503` 与 `32500–32503`，不会使用已有的 Syncthing 配置。测试在一台物理 Mac 上模拟四个节点。

0.2.4 曾在两台实体 Mac 的独立测试文库中验证事件触发的双向同步和附件传输；0.2.5 的命名变更通过核心、隔离传输、生命周期与启动检查。首次启动会核对现有文库和历史，所需时间取决于数据量。详见 [验证记录](VALIDATION.md)。

生命周期检查使用独立配置与端口 `29784` / `33784`，验证正常退出、显式停止引擎、强制结束主程序后的引擎清理，以及重新启动保留设备身份。启动检查使用已构建的 app 连续验证六轮自动启动与界面连接刷新。

可用 `VAULTSYNC_HOME=/绝对/测试目录` 覆盖本机数据位置。附加 `--demo` 会在该测试目录中生成示例文库和两条冲突分支，便于检查界面；必须同时指定覆盖目录，避免在正式数据中创建示例。
